Environment — read this first

Everything runs in WSL Ubuntu, not Windows. The starter spawns pi.cmd / npm.cmd with shell: false, which Node blocks on Windows (spawn EINVAL). On native Windows, Pi never launches and the build / dev-server checks always fail. Judges run Linux containers anyway.

Phase F — Improve the harness

This is the actual contest. Repeat until runs are reliable and cheaper.

Step 19. Work in solution/ and app-template/

Prompt, skill, extensions — plus domain-neutral primitives in app-template/, which the model never has to generate. Optional later: replace src/ if you bring your own runner, but keep the same result.json contract.

More than one Pi call per run means you must sum usage across every event stream into result.json. Judges recompute from Pi sessions and gateway records and treat disagreement as a failed audit.

Step 20. Re-run

npm run challenge

Step 21. Check in this order

  1. Did Pi finish (pi_exit_code 0)?
  2. Did Vitest pass with at least one real test (no skip/todo)?
  3. Did npm run build pass?
  4. Did http://localhost:3000 come up?
  5. Did result.json validate?
  6. Did token totals go down?

Step 22. Prioritize upgrades in this order

  1. Reliability on unseen ideas (test → repair → retest)
  2. Cover implied journeys without dropping them
  3. Record ambiguity in assumptions
  4. Move generated code into app-template/ — output tokens are weighted heaviest
  5. Fewer turns, not just fewer bytes; each turn re-sends the conversation
  6. Cache-stable prompts (keep the prefix byte-identical)
  7. Domain-neutral CRUD primitives — never book-specific vocabulary
  • The mvp-builder skill is injected as name + description + path only. The model spends a read call to load it, and may skip it. Inlining removes a round trip.
  • --system-prompt replaces Pi's default instead of appending, but the default is only ~1.5 KB and its docs block is already stripped. Minor lever.
  • Do not let the model read engine source; document the config shape in AGENTS.md. Reads stay in context for every later turn.

Step 23. Constraint checklist

  • No new npm packages in the generated app
  • No leftover npm run dev process
  • Do not write result.json from the agent
  • Agent writes report.partial.json only
  • Single-user local POC unless the idea requires more

Step 34. Challenge → analyze → export

Export is manual after each challenge (unless you use experiment publish — Step 36).

npm run challenge
# …wait until finished…
ls -1dt artifacts/runs/*/ | head -1    # note the run-id folder name
npm run analyze -- <run-id>
npm run export:run -- <run-id> --approach A-baseline-1
  • Export file: artifacts/exports/<run-id>.json
  • Schema: agentcofounder.run_export.v2 (preferred — includes efficiency.action_flow[]) or legacy v1
  • --approach = experiment arm label — structured names for Line / Experiment filters, e.g. A-baseline-1, A-autoverify-owned-2, rtl-control-3, rtl-cleanup-2. Avoid generic base. Optional env: RUN_APPROACH=…
  • Up-to-date export tooling adds meta.classification (line, experiment, display label). Ratings, comments, and exclude flags are entered in the runs app or seed script — not in the export file

Option B — bulk publish from WSL (re-export + seed prod DB):

export HACKATHON_ACCESS_CODE='…'   # team key — never commit
export HACKATHON_AUTHOR=paul

# One run: export JSON + POST upsert by run_id
npm run publish:run -- 2026-08-22T11-17-34-089Z --approach rtl-control-1

# Whole experiment arm(s): re-export reps from manifest → sync manifest → seed → backfill
npm run publish:runs -- --exp1-rtl

publish:runs calls GreenCastle seed_runs_from_artifacts.py then backfill_classification.py. Re-running is safe (upsert by run_id). Set RUNS_APP_ROOT if the frontend repo is not at the default Windows mount path. After publish, scripts print a view: link per run ( agentcofounder-hackathon.vercel.app/runs/<uuid>). Lookup: python3 scripts/print-run-frontend-links.py <run-id> (harness) or npm run links:runs -- <run-id> (runs app). Optional FRONTEND_BASE.

Compare on Runs (filter by line / experiment / branch) or Cohort (?preset=exp1-rtl for Experiment 1 rtl-control vs rtl-cleanup).

Step 36. Run a matched experiment cohort

For A/B arms (e.g. Phase F), use the experiment runner — manifest tracks reps under artifacts/experiments/<arm>/.

# Example: Experiment 1 — RTL cleanup vs control
npm run experiment:run -- --arm rtl-control --reps 5 --provider zai
npm run experiment:run -- --arm rtl-cleanup --reps 5 --provider zai
npm run experiment:report -- rtl-control rtl-cleanup

# Publish all reps to the runs app when done
npm run publish:runs -- --exp1-rtl
  • Hold constant: provider, model, idea file, timeout, settings — one change only per experiment
  • Approach labels: rtl-control-1 … rtl-cleanup-5 (Line F, experiments exp1-rtl-control / exp1-rtl-cleanup)
  • Export-only (no DB): ./scripts/publish-experiment-runs.sh --exp1-rtl without --seed
